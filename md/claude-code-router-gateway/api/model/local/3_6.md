## Qwen3-0.6B 特点

**Qwen3-0.6B** 是阿里 Qwen3 系列中的**最小稠密模型**，核心规格：

| 项目 | 值 |
|---|---|
| 参数量 | 600M |
| 架构 | Dense（非 MoE） |
| 层数 | 24 |
| 隐藏维度 | 1,024 |
| FFN 中间层 | 3,072 |
| 注意力 | **GQA**：16 Query heads + **8 KV heads** |
| 词汇量 | 151,936 |
| 上下文长度 | **32,768**（约 33K） |
| 量化（Q8_0）| 约 **600MB** 权重内存 |
| 激活函数 | Swish |
| 位置编码 | RoPE（theta=1M） |

亮点是用了 **GQA**（Grouped-Query Attention），8 个 KV heads 共享给 16 个 Query heads，大幅减少 KV cache 内存，同时保持不错的 attention 质量。0.6B 这种小模型用 GQA 而非 MHA，是非常合理的设计取舍。

## llama.cpp 线程参数详解

你配置了 `n_threads=1, n_threads_batch=1`，想省 CPU 和内存。**但这里有一个关键误解：**

### `n_threads` vs `n_threads_batch`

| 参数 | 使用阶段 | 作用 |
|---|---|---|
| `n_threads` | **逐 token 生成阶段**（decode） | 控制每次生成 1 个 token 时用多少线程 |
| `n_threads_batch` | **prompt 处理 / 批量计算阶段**（prefill） | 控制 ingest prompt、embedding、batch eval 时用多少线程 |

**它们都不影响内存占用**，只影响 CPU 占用和计算速度。

### 真正影响内存的是这些：

| 参数 | 影响 |
|---|---|
| `n_ctx`（你设了 15868） | KV cache 内存 = `n_ctx × 2 × num_layers × kv_head_dim × sizeof(float)` |
| `n_batch` | 一次处理多少 token，影响计算 buffer |
| `use_mmap: true` | 模型权重不加载到 RAM，而是映射到磁盘，按需 page-in，大幅降低 RAM 占用 |
| `mlock: false` | 不锁住物理内存，允许swap |

### 你设置了 `n_threads=1` 实际效果

```
prompt 处理阶段（prefill）：1 个线程，慢
逐 token 生成阶段：1 个线程，慢
CPU 占用：低（但不是因为省内存，而是因为算得慢）
内存占用：几乎不变（线程栈每个就几 MB，不是内存大户）
```

如果你用了 `use_mmap: true`，**内存占用主要是 KV cache**：
- Qwen3-0.6B GQA，8 个 KV heads，head_dim=128，24 层
- KV cache 每 token 约 `8 × 128 × 24 × 2（K+V）× 2bytes（FP16）≈ 98KB`
- 15868 ctx 满载 KV cache ≈ **1.5GB**

### 为什么减少线程没省内存？

CPU 线程的内存开销主要是**线程栈**（默认 1-8MB/线程），两个线程加起来撑死多占十几 MB。相比权重（Q8_0 约 600MB）+ KV cache（1.5GB）完全是九牛一毛。

**真正省内存的手段是：**
1. **减小 `n_ctx`**（直接减少 KV cache）
2. **`use_mmap: true`**（权重不占 RAM，按需加载）
3. **降低量化精度**（Q8_0 → Q4_K_M 可以省 30-40% 权重内存）
4. **`mlock: false`**（允许不常用的内存在内存紧张时被 swap 出去）

**省 CPU 的手段才是调线程数**：`n_threads=1` 确实让 CPU 占用低，但代价是生成速度变慢。如果你在意响应速度，可以把 `n_threads` 设为 CPU 物理核心数，`n_threads_batch` 可以设更高（prompt 处理并行度高，收益更大）。
