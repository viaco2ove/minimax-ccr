# minimax-ccr 模型分流 / 请求路由机制分析报告

## 一、总体架构

项目采用**双层分流**设计：

- **层 1 - 路由引擎（RoutingEngine）**：面向"一次请求选 provider:model"，按 `priority` 顺序匹配 scenario / tool_routing / keyword_routing / default，先命中先返回。服务于非 workflow 直连路径及 workflow 各阶段的兜底。
- **层 2 - 工作流（Workflow）+ 分流器（Splitter）**：`workflow.enabled=true` 时请求进入多步骤协作流程，每步由 `_get_stage_routes` 决定 provider:model 列表；`splitter`（默认 semantic_splitter）在 execute_solve/chat_intention 阶段优先做"意图级"语义分流，命中才用，未命中回退路由引擎。

配置文件 `.gateway.json` 顶层键：`server / env / providers / routing / quota / workflow`，其中 `routing` 与 `workflow` 是分流核心。

## 二、routing 配置如何被消费（.gateway.json）

`routing` 键含：`priority / default / scenarios / tool_routing / keyword_routing / splitter`，均在 `router/engine.py` 的 `RoutingEngine` 与 `main.py` 中被消费：

| 配置项 | 消费位置 | 作用 |
|---|---|---|
| `priority` | engine.py L30-33 | 分流策略匹配顺序，当前为 `["scenario","tool_routing","keyword_routing","default"]` |
| `default` | engine.py `_match_default` L130 | 兜底路由 `minimax:MiniMax-M2.7` |
| `scenarios` | engine.py `_match_scenario` L55 | 按请求场景（compact/long_context/image/think/web_search/background）匹配 route+fallback |
| `tool_routing` | engine.py `_match_tool_routing` L67 | 按 tool 调用名+子命令匹配（cheap/standard/complex_tasks） |
| `keyword_routing` | engine.py `_match_keyword_routing` L109、classifier/keyword.py | 按关键词规则匹配（架构类→bigmodel、/compact→minimax_long） |
| `splitter` | main.py init_app L251、splitter/factory.py | `active_strategy="semantic_splitter"`，`semantic_splitter.type="local"`、`model_name="moka-ai/m3e-small"`、`hf_endpoint="https://hf-mirror.com"`、`trust_remote_code=true` |
| `workflow` | main.py `_handle_workflow` L1926 | 各阶段 provider 列表：intention_analyze=[bigmodel:GLM-5.3, minimax:MiniMax-M2.7]、analyze_plan=[bigmodel:GLM-5.3-Flash, minimax:MiniMax-M2.7]、chat_intention=[minimax:MiniMax-M3, ...]、execute_solve=[minimax:MiniMax-M2.7, bigmodel:GLM-5.3-Flash] |

**`keyword_routing` 配置被三处消费**：① 路由引擎 `_match_keyword_routing`（engine.py L109）；② 分类器 `KeywordClassifier`（classifier/keyword.py L14）；③ 各 Splitter 的 `_resolve_route_from_keywords`（semantic_local/semantic/llm 用命中的语义关键词去 `rules` 里匹配 route）。rule 0 命中架构/优化/设计/重构等词 → `bigmodel:GLM-5.3-Flash`；rule 1 命中 `/compact` → `minimax_long:MiniMax-M3`。

## 三、router 模块：职责与执行顺序

### engine.py — RoutingEngine（233 行）
- `route()` **L27**：按 `_priority` 顺序调用匹配器，**先命中先返回**；`default` 命中直接经能力检查返回；全未命中兜底 default。核心顺序 = `_match_scenario → _match_tool_routing → _match_keyword_routing → _match_default`。
- `_match_scenario` **L55**：`tags.scenario` 非空即查 `scenarios` 表。
- `_match_tool_routing` **L67**：遍历 tool_routing 规则，`match_mode=any` 时任一 tool 命中即返回（含 subcommand 模式，如 `Bash(git status)`）。
- `_match_keyword_routing` **L109**：遍历 `keyword_routing.rules`，`any` 模式下 rule 关键词与 `tags.keywords` 有交集即命中。
- `_match_default` **L130**：返回 `default` 路由。
- `_build_route_result` **L140**：解析 `route:model` 并构建 `fallback_chain`（列表的 tuple 列表）。
- `_check_capabilities` **L166**：若主 provider 不满足 thinking/vision/tool_use 能力，从 fallback_chain 找第一个满足能力的 provider，并用"满足能力"的子集重建 fallback_chain；全部不满足则仍用原 route（由 adapter 剥离不支持内容）。

### fallback.py — FallbackRouter（174 行）
- `call_provider_streaming` **L92**：按 `route_list` 顺序尝试，任一 provider 成功（async for 正常结束）即返回；失败/异常/空 chunk 则尝试下一个。关键过滤：
  - **max_context 检查**：`_calc_msgs_tokens` 估算 token，超过 provider 的 `capabilities.max_context`（经 `_get_provider_max_context` L46 实时 load_config 获取）直接跳过该 provider，全超则抛 RuntimeError。
  - 发送前调用 `clean_request` 清理空 text/thinking block。
- 核心原则（文件头注释）：一次 CLI 请求只发一个请求到一个 provider，200=成功，错误=尝试下一个。

### req_cli_pre.py — 请求预处理器（73 行）
- `clean_request` **L14**：遍历 messages，剔除**空 text block** 与 **thinking block**（部分 provider 不支持），在发送前净化请求体。

## 四、classifier 模块：各分流器判定规则

### scenario.py — ScenarioClassifier（117 行）
`classify` **L17** 按优先级依次判定：
1. **compact**（L53 `_has_compact`）：最后一条 user 消息含 `/compact` → `minimax_long:MiniMax-M3`；
2. **long_context**（L100 `_estimate_tokens`）：`json.dumps(request)` 字符数 // 4 估算 token，超 `scenarios.long_context.threshold`（默认 60000，配置里为 **122000**）→ `minimax_long:MiniMax-M3`；
3. **image**：最后一条 user 消息含 image block（在 thinking 前检测，因 Claude Code 总带 thinking）→ `bigmodel:GLM-5.3-Flash`；
4. **think**：`request.thinking` 非空 → `bigmodel:GLM-5.3-Flash`；
5. **web_search**：tools 含 `web_search*` → `minimax:MiniMax-M3`；
6. **background**：请求 model 含 `haiku` → `minimax:MiniMax-M2.7`。

`extract_tags` **L105** 产出 `RequestTags`（scenario/has_thinking/has_web_search/has_images/token_count/model_hint）。

### keyword.py — KeywordClassifier（63 行）
`classify` **L14**：提取 **system + 所有 user 消息**文本，对 `keyword_routing.rules` 每个关键词做**小写子串匹配**，返回命中关键词列表。`extract_tags` **L60** 包装之。只做子串（非单词边界），语义更宽。

### tool_type.py — ToolTypeClassifier（132 行）
`classify` **L23**：从 messages 扫描三种来源提取 tool 名+子命令：
- `tool_result`：按 `tool_use_id` 反查先前 `tool_use` 得到 name；
- `tool_use`：取 `name` + `_extract_subcommand`（Bash→command、Read/Write/Edit→file_path、Glob→pattern、Grep→path）；
- `tool_calls`（OpenAI 格式）：取 `function.name` + 解析 arguments 提取 subcommand。
支持 `ToolName(subcommand)` 精确模式与通配符。`extract_tags` **L129**。

## 五、splitter 模块：切分策略与参与分流方式

`factory.py` `create` **L36** 按 `active_strategy` 惰性创建（`_ensure_builder` **L24**）：`keyword_splitter` 预加载，`semantic_splitter` 懒加载 `semantic_local.SemanticSplitterLocal`，`llm_splitter` 懒加载 `llm.LLMSplitter`；未知策略回退 `keyword_splitter`。全部实现统一基类 `Splitter`（base.py **L20**），返回 `RoutingDecision`（base.py **L11**：`intent/route/matched_rule/matched_reason/fallback`）。

**参与分流的入口**：`main.py` 的 `_detect_workflow_intent` **L1280** 与 `_try_splitter_route` **L1428**。

| 策略 | 判定逻辑 | 降级 |
|---|---|---|
| **semantic_local.py**（SemanticSplitterLocal，L43 `detect`） | 本地 sentence_transformers 对用户文本与各 category 关键词编码，`_match_keywords` **L84** 每 category 取 top3 且余弦相似度 ≥ threshold(0.5)；`_resolve_route_from_keywords` **L125** 用"**最高分归属法**"定 intent（chat_intention 最高分 vs task 四类最高分，高者归属，取代旧计数法），再用命中关键词匹配 keyword_routing.rules 得 route | `_load_model` **L191** 失败置 `_load_failed=True` 永久不再加载，`_keyword_fallback` **L306** 降级 KeywordSplitter |
| **semantic.py**（SemanticSplitter，L46 `detect`） | 逻辑同 local 版，但用**外部 embedding API**（`embedding_api`）取向量（`_get_embedding` L133），threshold 默认 0.6 | 无 API/向量获取失败 → `_keyword_fallback` 降级 KeywordSplitter |
| **keyword.py**（KeywordSplitter，L22 `detect`） | 从 `keywords.json` 的 `workflow_intent.chat_intention` / `intention_analyze` 关键词做**单词边界匹配**计数：task_score > chat_score 走 task 路由，chat_score>0 走 chat，否则 default；`_resolve_route` **L73** 按 intent 从 rules 找 route | 无（本身就是最底降级） |
| **llm.py**（LLMSplitter，L123 `detect`） | 调配置 LLM（或本地 GGUF）输出关键词 JSON，解析后按 rules 路由 | 全部失败降级 KeywordSplitter |
| **workflow.py**（WorkflowSplitter，L16 `detect_intent`） | 旧版关键词意图检测，返回 `"chat"/"task"` 字符串，仅作 `_detect_workflow_intent` 中 splitter 缺失时的兜底包装 | 无 |

## 六、语义切分降级链路（关键）

```
semantic_splitter (SemanticSplitterLocal / SemanticSplitter)
   ├─ 模型 import/加载失败 或 encode 异常 / API 无 key / 向量获取失败
   │      → _keyword_fallback → KeywordSplitter.detect
   │            └─ workflow_intent 关键词计数 → 走 keyword_routing.rules 或 default
   ├─ 提取文本为空 / _load_failed 置位（永久）→ 同上 KeywordSplitter
   └─ 模型正常 → 语义相似度匹配 → 命中规则路由 / 未命中 no_match 回退路由引擎
```
另外：`_try_splitter_route`（main.py L1428）中，splitter 决策还须过 provider 能力检查（vision/thinking），不满足则沿 `decision.fallback` 降级，全不满足返回 None 交给 `_resolve_route_with_meta` 路由引擎。

## 七、完整调用链（HTTP 入口 → 选定 provider:model）

### 启动
`run_ccrg.py`（注入 ml_lib → `from ccrg.main import run`）→ `main.py` `run` **L2786** → `init_app` **L251**：load_config → ProviderRegistry → **RoutingEngine** → 创建 `_workflow_splitter`（SplitterFactory.create）→ 若 semantic_splitter 则预加载 embedding 模型。

### HTTP 入口
- `/v1/messages` → `handle_messages`（init_app 内联）→ **`_handle_request` L520**
- `/v1/chat/completions` → `handle_chat_completions` → `_convert_openai_to_anthropic` **L2661** → `_handle_request`

### 非 workflow 直连路径（workflow.enabled=false 时）
`_handle_request` **L520**：
1. 检查 `workflow.enabled`（配置当前为 true，故主路径走 workflow）
2. `_classify_request` **L1258**：scenario.extract_tags → tool_type.extract_tags（intention_analyze 阶段跳过防劫持）→ keyword.extract_tags → 产出 `RequestTags`
3. `_routing_engine.route(tags)` → `RouteResult(provider, model, fallback_chain)`
4. `_registry.get(provider)` 取 provider 配置，按 protocol 选 adapter（AnthropicAdapter/OpenAIAdapter）
5. 发送：`providers_to_try = [主] + fallback_chain`；流式走 `_handle_streaming_with_fallback` **L742**（含 400 剥功能重试 `_strip_unsupported_features`），非流式逐 provider POST，均失败返回 502。

### workflow 路径（当前主路径）
`_handle_request` L520 → **`_handle_workflow` L1926** → 内嵌 `workflow_stream_generator`（约 **L2530**）：
1. 从 `metadata.workflow_stage` 取 stage；无则 `_detect_workflow_intent` **L1280**（title 生成请求跳过 splitter 走 default `matched_rule=non_workflow_bypass`，否则 `_workflow_splitter.detect`）→ 结合 `_is_user_initiated_message` **L1655** 判定 stage（用户输入→intention_analyze，工具回调→`_infer_stage_from_context` **L1587**）
2. **`_get_stage_routes` L1330** 决定 `route_list + step_name + route_meta`：
   - `/compact` 请求 → scenarios.compact，且 override stage 为 execute_solve
   - lv1 scenario（compact/long_context/image）→ 走 scenarios 表
   - **intention_analyze / analyze_plan** → 直接用 workflow 配置列表（跳过 splitter 和路由引擎）
   - **execute_solve / chat_intention** → 优先 **`_try_splitter_route` L1428**（splitter 命中且能力满足才用，否则回退）；未命中再走 **`_resolve_route_with_meta` L1507**（内部再跑 `_classify_request` + `route()`），最后以 workflow 列表去重补 fallback
3. `FallbackRouter(route_list, ...).call_provider_streaming`（fallback.py L92）按序流式调用，超 max_context 跳过、失败切下一个
4. 阶段结束注入 `{workflow_stage:next_stage}` tag（仅对语义路由结果注入，keyword_routing/non_workflow_bypass 命中除外），驱动 CCRG 进入下一阶段。

## 八、分流优先级总结

1. **场景分流（scenario）**：compact > long_context > image > think > web_search > background
2. **工具分流（tool_routing）**：cheap_tasks / standard_tasks / complex_tasks（any 命中）
3. **关键词分流（keyword_routing）**：架构类 / compact 类规则
4. **默认路由（default）**：`minimax:MiniMax-M2.7`
5. **workflow 阶段内**：intention_analyze/analyze_plan 直用配置；execute_solve/chat_intention 优先 **splitter 语义分流**（semantic→keyword 降级），未命中回退上述 1-4
6. **能力降级（capability fallback）**：任何命中 provider 不满足 thinking/vision/tool_use 时，沿 fallback_chain 找满足者
7. **运行时降级（FallbackRouter）**：provider 报错 / 超 max_context / 空响应 → 尝试 route_list 下一项
