# 意图识别权重

请求到达 CCRG 后，按优先级从高到低逐层检测，决定最终路由到哪个 provider:model。

---

## 优先级总览

| 优先级 | 意图              | 检测方式 | 路由目标 | 说明 |
|--------|-------------------|----------|----------|------|
| **lv1** | /compact          | `_is_compact_request()` | `minimax_long:MiniMax-M3` | 长上下文压缩，需要最大上下文处理能力 |
| **lv2** | image,long_context   | `_classify_request().scenario == "image"` | `xiaomi:mimo-v2.5-pro` | 含图片的请求，需要 vision 能力 |
| **lv3** | intention_analyze | `{workflow_stage:intention_analyze}` 或 auto-detect | workflow 配置 | 分析用户意图阶段 |
| **lv3** | analyze_plan      | `{workflow_stage:analyze_plan}` 或 auto-detect | workflow 配置 | 分析执行结果阶段 |
| **lv4** | execute_solve     | auto-detect（tool_use 模式） | splitter 决策优先 | 执行解决方案阶段 |
| **lv4** | chat_intention    | auto-detect（纯对话） | splitter 决策优先 | 闲聊意图 |
| **lv5** | default fallback  | - | `execute_solve` workflow 配置 | 所有检测都未命中时兜底 |

## 各层级详细说明

### lv1 — /compact（最高优先级）

**触发条件**：请求 body 中最后一条 user 消息包含 `\compact` 字符串。

```python
def _is_compact_request(body: dict) -> bool:
    messages = body.get("messages", [])
    for msg in reversed(messages):
        if msg.get("role") != "user":
            continue
        content = msg.get("content", "")
        # 检查字符串或 text block
        if isinstance(content, str):
            if "\compact" in content:
                return True
        elif isinstance(content, list):
            for block in content:
                if isinstance(block, dict) and block.get("type") == "text":
                    if "\compact" in block.get("text", ""):
                        return True
        break
    return False
```

**路由目标**：从 `.gateway.json` 的 `scenarios.compact` 读取：
```json
"compact": {
  "route": "minimax_long:MiniMax-M3",
  "fallback": ["xiaomi:mimo-v2.5", "xiaomi:mimo-v2.5-pro"]
}
```

**为什么最高优先级**：compact 请求通常包含 200+ 条对话历史，需要最大的上下文处理能力。检测到后直接跳过所有其他逻辑（包括 splitter、workflow stage 等）。

---

### lv2 — image（图片场景）

**触发条件**：`_classify_request()` 检测到 `tags.scenario == "image"`。

图片检测在 `_classify_request` 中通过扫描 `messages` 里的 `image_url` 或 base64 图片数据块实现。

**路由目标**：从 `.gateway.json` 的 `scenarios.image` 读取：
```json
"image": {
  "route": "xiaomi:mimo-v2.5-pro",
  "fallback": ["mmx:MiniMax-M2.7", "xiaomi:mimo-v2.5"]
}
```

**注意**：image 和 compact 互斥，实际请求只会命中其中一个。

---

### lv3 — workflow stage 配置（固定路由）

这两个 stage **不经过 splitter**，直接使用 `.gateway.json` 的 workflow 配置：

| stage | 配置字段 | 默认路由 |
|-------|----------|----------|
| `intention_analyze` | `workflow.intention_analyze` | `xiaomi:mimo-v2.5-pro` |
| `analyze_plan` | `workflow.analyze_plan` | `xiaomi:mimo-v2.5-pro` |

**为什么不需要 splitter**：
- `intention_analyze` 是用户主动输入后的第一次请求，不需要语义判断
- `analyze_plan` 是执行完后的分析阶段，路由固定为配置值

**stage 来源优先级**：
1. 请求 `body.metadata.workflow_stage`（调用方显式指定）
2. `{workflow_stage:xxx}` tag（从最后一条 assistant 消息提取）
3. auto-detect（`_infer_stage_from_context` 推断）

---

### lv4 — execute_solve / chat_intention（splitter 决策）

这两个 stage 走 splitter 语义判断 + routing 引擎：

**流程**：
```
_try_splitter_route(body)
  → splitter.detect(body)  # semantic / keyword / llm splitter
    → matched_reason 包含 "no_match" / "no_keywords" → return None
    → 命中关键词 → 返回 route
  → 能力检查（vision / thinking）
  → 通过 → 用 splitter 决策
  → 不通过 → return None

↓ splitter 未命中或被跳过

_resolve_route_with_meta(body, stage)
  → routing 引擎（scenario / tool_routing / keyword_routing）
```

**splitter 决策被忽略的条件**：
- matched_reason 包含 `no_match` 或 `no_keywords`
- splitter 选择的 provider 不满足请求能力（无 vision 但请求有图片等）

---

### lv5 — default fallback

所有检测都未命中时，返回 `execute_solve` 的 workflow 配置作为兜底。

---

## 路由决策流程图

```
请求到达 _get_stage_routes(stage, body)
    │
    ├─ [lv1] /compact? ──是──→ scenarios.compact 路由
    │
    ├─ [lv2] image scenario? ──是──→ scenarios.image 路由
    │
    ├─ [lv3] stage == intention_analyze? ──是──→ workflow.intention_analyze
    ├─ [lv3] stage == analyze_plan? ──是──→ workflow.analyze_plan
    │
    ├─ [lv4] stage == execute_solve / chat_intention?
    │       ├─ splitter 命中? ──是──→ splitter 决策路由
    │       └─ splitter 未命中?
    │              ├─ stage == chat_intention? ──是──→ workflow.chat_intention
    │              └─ stage == execute_solve? ──是──→ routing 引擎
    │
    └─ [lv5] 以上全部未命中 → execute_solve workflow 配置兜底
```

---

## `{workflow_stage:xxx}` Tag 检测

CCRG 在每个阶段完成后，会在响应末尾注入 `{workflow_stage:<next_stage>}` tag。

**注入映射**：
| 当前阶段 | 注入 tag |
|---------|---------|
| intention_analyze | `{workflow_stage:execute_solve}` |
| execute_solve | `{workflow_stage:analyze_plan}` |
| analyze_plan | `{workflow_stage:execute_write}` |

**检测逻辑**：从 `body.messages` 中最后一条 assistant 消息的 text 块搜索 `{workflow_stage:(\w+)}`，以最后一个为准。

**优先级高于 auto-detect**：如果 tag 存在，直接使用 tag 的值，不走 `_infer_stage_from_context` 推断。
