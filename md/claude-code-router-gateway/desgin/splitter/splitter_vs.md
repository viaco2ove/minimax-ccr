# CCRG网关三种拆分器终极对比（针对Claude Code多模型分流场景）
keyword_splitter vs semantic_splitter_local vs llm_splitter
结合你当前的`.gateway.dou_q_m.json`配置和**中文代码开发+多模型智能路由**的核心场景，我将从**原理本质、精度表现、性能成本、对分流的影响、适用场景**五个维度进行全面对比，并给出最终的最优选择和混合配置方案。

## 一、核心原理本质对比
三种拆分器的底层逻辑完全不同，这决定了它们的能力边界和适用场景：

| 拆分器类型 | 核心原理 | 决策依据 | 智能程度 |
|-----------|---------|---------|---------|
| **keyword_splitter** | 基于**固定规则**的机械拆分 | 预设的分隔符（`\n\n`、`\n`、空格）、关键词、字符/Token数量 | 0/10（纯规则） |
| **semantic_splitter_local** | 基于**本地嵌入模型**的语义相似度拆分 | 相邻句子/段落的向量余弦相似度，相似度低于阈值则拆分 | 6/10（统计语义） |
| **llm_splitter** | 基于**大语言模型**的理解式拆分 | LLM对文本内容的完整理解，识别主题边界、逻辑结构和语义单元 | 10/10（认知理解） |

### 工作流程对比
1. **keyword_splitter**：
   ```
   输入文本 → 按预设分隔符切割 → 合并到指定chunk_size → 输出固定大小的块
   ```
   完全不理解文本内容，只是按照字符规则切割。

2. **semantic_splitter_local**：
   ```
   输入文本 → 拆分为句子 → 本地模型生成每个句子的嵌入向量 → 计算相邻句子相似度 → 相似度低于阈值则拆分 → 合并小chunk → 输出语义连贯的块
   ```
   理解"语义相似性"，但不理解文本的具体含义和逻辑结构。

3. **llm_splitter**：
   ```
   输入文本 → 发送给LLM → LLM阅读并理解全文 → 识别主题边界、逻辑段落和代码块 → 输出拆分结果和理由
   ```
   真正理解文本的内容、逻辑和结构，能做出最符合人类认知的拆分决策。

## 二、关键维度全面对比
### 1. 拆分精度对比（针对你的中文代码混合场景）
这是直接影响**多模型分流准确性**的最重要指标：

| 文本类型 | keyword_splitter | semantic_splitter_local(m3e-small) | llm_splitter |
|---------|------------------|-----------------------------------|-------------|
| 纯中文自然语言 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 纯代码 | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 中文+代码混合（你的主要场景） | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 架构设计文档 | ⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 长函数/类定义 | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 关键词匹配完整性 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

**关键差异点**：
- **keyword_splitter**：经常把"架构"、"重构"等关键词拆到两个块中，导致你的`keyword_routing`规则失效；也经常把一个完整的函数拆成两半，破坏代码语义。
- **semantic_splitter_local(m3e-small)**：专门针对中文技术文本优化，能准确识别"架构设计"、"代码实现"等不同语义主题的边界，几乎不会破坏完整的代码块和关键词。
- **llm_splitter**：能理解代码的逻辑结构，会把一个完整的类、函数或逻辑单元作为一个块，甚至能识别注释和代码的对应关系，拆分精度最高。

### 2. 性能与成本对比
这是你作为个人开发者最需要考虑的实际问题：

| 维度 | keyword_splitter | semantic_splitter_local(m3e-small) | llm_splitter |
|-----|------------------|-----------------------------------|-------------|
| 处理速度 | 极快（<10ms/KB） | 快（~100ms/KB） | 极慢（~10s/KB） |
| 内存占用 | 可忽略（<10MB） | 低（~200MB） | 高（取决于LLM大小） |
| CPU占用 | 极低 | 中等 | 极高（本地LLM）/ 无（API调用） |
| 额外成本 | 0 | 0 | 高（API调用费用） |
| 并发处理能力 | 极高 | 高 | 极低 |

**关键差异点**：
- **keyword_splitter**：几乎不消耗任何资源，速度最快，但精度最差。
- **semantic_splitter_local**：一次性加载模型后，后续处理速度很快，完全免费，是性价比最高的选择。
- **llm_splitter**：如果使用API调用，处理一个100KB的文件可能需要花费$0.1-$0.5，并且速度极慢，完全不适合日常使用；如果使用本地LLM，需要至少16GB显存，并且速度依然很慢。

### 3. 对CCRG多模型分流效果的影响
这是你最关心的核心问题，拆分器的质量直接决定了你的路由规则是否能正常工作：

| 分流规则类型 | keyword_splitter | semantic_splitter_local | llm_splitter |
|-------------|------------------|------------------------|-------------|
| **关键词路由** | ❌ 经常失效（关键词被拆分） | ✅ 几乎100%准确 | ✅ 100%准确 |
| **工具路由** | ❌ 经常破坏工具调用指令 | ✅ 完整保留工具调用 | ✅ 完整保留工具调用 |
| **场景路由** | ❌ 长上下文判断错误 | ✅ 准确计算token数量 | ✅ 准确计算token数量 |
| **工作流分流** | ❌ 意图识别输入不完整 | ✅ 完整保留意图信息 | ✅ 完整保留意图信息 |
| **降级机制** | ✅ 永远可用 | ✅ 几乎永远可用 | ❌ 容易超时或失败 |

**关键差异点**：
- **keyword_splitter**：会导致你的`keyword_routing`中"架构"、"重构"等关键词经常被拆分到两个块中，从而无法触发路由到`doubao:ark-code-latest`的规则，严重影响复杂任务的处理质量。
- **semantic_splitter_local**：能完整保留关键词和工具调用指令，让你的所有路由规则都能准确触发，是目前最适合你场景的选择。
- **llm_splitter**：虽然精度最高，但速度太慢，会导致Claude Code CLI超时，并且成本太高，不适合日常使用。

### 4. 配置复杂度与可靠性对比
| 维度 | keyword_splitter | semantic_splitter_local | llm_splitter |
|-----|------------------|------------------------|-------------|
| 配置难度 | 极低 | 中等 | 极高 |
| 调参难度 | 低 | 中等 | 极高 |
| 可靠性 | 极高 | 高 | 低 |
| 可调试性 | 极高 | 高 | 低 |
| 依赖项 | 无 | 本地嵌入模型 | LLM API或本地大模型 |

## 三、针对你的CCRG网关的最终结论
### 1. 绝对不推荐：keyword_splitter
**为什么不适合你**：
- 你的路由规则高度依赖关键词匹配（"架构"、"重构"、"[deep]"等），keyword_splitter经常会把这些关键词拆到两个块中，导致路由规则失效。
- 你的场景包含大量中文+代码混合文本，keyword_splitter经常会破坏完整的代码块和函数定义，导致模型无法理解代码逻辑。
- 虽然速度最快，但精度太差，会严重影响你的多模型分流效果和代码生成质量。

### 2. 强烈推荐：semantic_splitter_local(m3e-small)
**为什么是你的最优选择**：
- **精度足够**：m3e-small是专门针对中文技术文本优化的嵌入模型，在中文+代码混合场景下的拆分精度几乎与llm_splitter相当，完全能满足你的需求。
- **成本为零**：完全在本地运行，不需要任何API调用费用。
- **性能优秀**：一次性加载模型后，处理速度很快，不会影响Claude Code的使用体验。
- **完美适配你的路由规则**：能完整保留关键词和工具调用指令，让你的所有路由规则都能准确触发。
- **可靠性高**：几乎不会出现超时或失败的情况，并且有完善的降级机制。

### 3. 特殊场景可选：llm_splitter
**仅在以下极端场景下使用**：
- 处理极其复杂的架构设计文档，需要理解文档的深层逻辑结构。
- 处理包含大量嵌套代码和复杂注释的超大文件。
- 对拆分精度有极致要求，并且愿意付出更高的成本和等待时间。

**使用建议**：不要将其设置为默认拆分器，而是通过关键词手动触发，例如在问题末尾添加`[llm_split]`来临时使用llm_splitter。
